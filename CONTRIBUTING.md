# Contributing to Stoic

Thanks for taking the time. This file covers how to get set up and what a change is expected to
come with. If something here is out of date or unclear, that's a bug — please open an issue.

## Setup

Stoic uses **Yarn 4** via Corepack. Never `npm install` or `pnpm install` — the lockfile is Yarn's.

```bash
corepack enable
yarn install
yarn test
```

Node 24 is what CI runs (`.nvmrc`). The published package supports Node 18+.

## Commands

| Command | What it does |
| --- | --- |
| `yarn test` | Vitest — unit tests **and** the `*.test-d.ts` type tests |
| `yarn test:coverage` | The same, with coverage and the thresholds CI enforces |
| `yarn typecheck` | `tsc --noEmit`, plus a separate typecheck of every example |
| `yarn lint` | Biome, in CI mode (no writes) |
| `yarn format` | Biome, with `--write` |
| `yarn build` | tsdown — dev build in `dist/`, minified production build in `dist/prod/` |
| `yarn size` | Per-entry-point gzip sizes of `dist/prod` |
| `yarn size:check` | The CI size gate, against `size-baseline.json` |
| `yarn check:package` | `publint` + `attw` against the packed tarball |
| `node scripts/api-drift.mjs` | Fails if a public export is missing from `docs/api-reference.md` (build first) |
| `yarn bench` | Builds, then runs `scripts/bench.mjs` against `dist/` |
| `yarn changeset` | Records a changeset for a user-facing change |

## What a change should come with

**Tests.** Every behaviour change needs one, in the co-located `*.test.tsx` file, and run the whole
suite rather than the file you touched. Type-level behaviour goes in `src/types.test-d.ts` — runtime
tests do not cover it.

Two things are worth testing more carefully than they look:

- **Rerender counts.** "Only subscribers of changed derived values rerender" is the core promise. If
  you touch subscription or dirty-tracking, assert on render counts, not just on values.
- **Regression guards.** A test for a bug fix should fail against the unfixed code. If it passes
  either way, it is pinning nothing — check it by reverting your fix and re-running.

**A changeset**, for anything user-facing: `yarn changeset`. Patch for fixes, minor for additions,
major for breaking changes. See [Versioning](./docs/versioning.md) for what counts as breaking.

**A benchmark, if you touched a hot path** in `src/stoic.ts` (set, notify, derived recompute,
subscription dispatch). Measure it — do not reason about it:

```bash
yarn bench --save base.json   # on the unmodified tree
# apply your change
yarn bench --base base.json
```

Run both halves in the same session. Run-to-run noise is ±5–12%, so a saved baseline from yesterday
will mislead you, and anything under 5% is not a result. An optimization that doesn't show up in
`yarn bench` is complexity, not a win — revert it.

## House style

- **Comments explain _why_.** Invariants, constraints, and things that were tried and rejected. The
  code already says what it does. Several comments in `src/stoic.ts` record measured alternatives
  that lost; that history is deliberate — please add to it rather than deleting it.
- **Biome owns formatting.** 2-space indent, double quotes, 100 columns. Don't fight it.
- **No runtime dependencies.** Not one.
- **No suppressions.** The config extends `@tsconfig/strictest`. If you genuinely need `any`, an
  `as`, or a `@ts-expect-error` in `src/`, leave a comment justifying it.
- **Dev-only code goes behind `DEV`** from `src/env.ts`, shaped as `if (DEV)` so the production
  build folds the branch — and its message strings — away entirely.
- **Keep diffs focused.** Don't reformat or "improve" code the change doesn't need to touch.

## Design principles

Before proposing a feature, it's worth reading [`docs/philosophy.md`](./docs/philosophy.md). The
short version:

- **If it can be a plugin, it must be a plugin.** New public API needs a much stronger case than new
  internal code.
- **The API is the product.** Prefer one obvious way to do something. Adding a second way to express
  something that already works is a cost, not a feature.
- **Everything stays tree-shakeable.** `sideEffects: false` is declared: no module-level side
  effects, no top-level mutation, entry points stay independent.
- **Question the architecture** — but change it with benchmarks and tests, not intuition.

## Adding an entry point

Public entry points are fixed: `index`, `react`, `plugins`, `plugins/persist`, `plugins/devtools`,
`tools`. Adding one means updating four places together:

1. `tsdown.config.ts`
2. `package.json#exports` (generated by tsdown's `customExports` hook)
3. the `ENTRIES` map in `scripts/size.mjs`
4. the `ENTRIES` map in `scripts/api-drift.mjs`

Miss one of the last two and the new entry point simply goes unmeasured and unchecked — CI stays
green. Adding a public entry point is a change to the stable surface, so it needs a
[major-version](./docs/versioning.md) conversation first.

## Releasing

Maintainers only. Changesets drives it: merging to `main` opens (or updates) a release PR, and
merging that publishes to npm via OIDC trusted publishing. Don't bump versions by hand.
